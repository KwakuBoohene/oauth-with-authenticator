# oauth-with-authenticator

A from-scratch **single sign-on lab**: an [OAuth] 2.1 / OpenID Connect provider
that logs users in with **passkeys ([WebAuthn])**, a handful of client apps that
use it for [SSO], and our own **passkey authenticator** that Chrome talks to
through an extension.

The point is to *understand* the protocols, so almost nothing is imported:
[SHA-256], [HMAC], [P-256] [ECDSA], [AES]-[GCM], [CBOR], [DER], [COSE], [JOSE]/JWT, WebAuthn, [CTAP2]
and OAuth/OIDC are all implemented by hand with heavily commented code.

> ⚠️ **Learning code, not production code.** The crypto is not constant-time,
> nothing has been audited, and shortcuts are documented in comments.

**Status:** planning complete, implementation not started.

> 📖 New to the jargon? Every acronym (CBOR, [PKCE], [UV], …) is explained in plain
> English in **[docs/glossary.md](docs/glossary.md)**.

## Architecture

```
   Chrome (host machine)
   ┌──────────────────────────────────────────────┐
   │ pages: auth / app-a / app-b                  │
   │ extension (MV3) ── native messaging ──┐      │
   └───────────────┬───────────────────────┼──────┘
                   │ HTTP                  │ stdin/stdout (JSON)
                   ▼                       ▼
 ┌──────────────── Docker ────────────┐  ┌──── host ─────────────────────┐
 │ authserver   :8080  (Go)           │  │ pk-native-host (Rust)         │
 │   OIDC provider + WebAuthn RP      │  │   WebAuthn client role        │
 │ app-a        :8081  confidential   │  │   CTAP2 authenticator         │
 │ app-b        :8082  SPA, public    │  │   P-256 / AES-GCM / CBOR      │
 │ resource-api :8083  JWT-protected  │  │   encrypted credential store  │
 └────────────────────────────────────┘  └───────────────────────────────┘
```

The three [WebAuthn] roles are all ours:

| WebAuthn role | Lives in |
|---|---|
| Relying Party (verifies passkeys) | `server/internal/webauthn` |
| Client (builds `clientDataJSON`, checks origin vs [RP ID]) | `authenticator/crates/pk-client` (+ `extension/` plumbing) |
| Authenticator (holds keys, signs) | `authenticator/crates/pk-ctap2` |

Watch out for the term **relying party**, which means different things in the
two protocols. In WebAuthn it is the server that verifies passkeys (our
`authserver`). In [OIDC] it is the client app that trusts ID tokens (`app-a`,
`app-b`).

## Repository layout

```
server/          Go module: authserver, app-a, app-b, resource-api, internal libs
authenticator/   Rust workspace: no_std crates + native-messaging host
extension/       Chrome MV3 extension (vanilla JS, no build step)
e2e/             End-to-end tests (Go plays browser + extension)
docker/          Dockerfiles
scripts/         Dev scripts (vector fetcher, LOC checker, native-host installer)
testdata/        Shared test vectors (NIST, RFC, Wycheproof)
docs/            Glossary (every acronym explained), architecture notes, manual test checklists
```

## Quick start (once implemented)

```sh
make up          # build + start authserver, app-a, app-b, resource-api in Docker
open http://auth.localhost:8080
make test        # Go + Rust unit tests
make e2e         # full register → login → OAuth → API flow in Docker
make down
```

To use **our** authenticator instead of Chrome's built-in passkeys:

```sh
make install-native-host   # builds pk-native-host, registers it with Chrome
# then load extension/ as an unpacked extension at chrome://extensions
```

## Requirements

- Docker (with Compose)
- Go 1.26+ and Rust stable (for local builds/tests and the native host)
- Chrome. `*.localhost` names resolve to 127.0.0.1 automatically.

## Specs implemented

[FIPS] 180-4 ([SHA-256]) · [RFC] 2104 ([HMAC]) · RFC 5869 ([HKDF]) · FIPS 186-5 + [SEC] 1 ([P-256] [ECDSA]) ·
RFC 6979 (deterministic ECDSA) · FIPS 197 + [SP] 800-38D ([AES]-[GCM]) · RFC 4648 (base64url) ·
RFC 8949 ([CBOR]) · RFC 9052/9053 ([COSE]) · [X.690] ([DER]) · RFC 7515/7517/7519/7638 ([JOSE]) ·
[W3C] [WebAuthn] Level 3 · [FIDO] [CTAP] 2.1 · RFC 6749 / [OAuth] 2.1 draft · RFC 7636 ([PKCE]) ·
RFC 9068 ([JWT] access tokens) · RFC 7009 / 7662 (revocation, introspection) · RFC 9207 (iss) ·
OpenID Connect Core / Discovery / [RP]-Initiated Logout / Back-Channel Logout.
